# Эхо при звонках на OnePlus 6T: в драйвере по умолчанию выбрана топология, которой нет в заводской калибровке

## Окружение

- Устройство: OnePlus 6T (fajita), загрузчик разблокирован
- Образ: `alt-mobile-phosh-sdm845-latest-aarch64.tar.xz`, b2sum `0283b13f32f174914eea36c9e6ce4cf5181ba6bbab20b510c4c36582baefdf4f...`
- Загрузчик: `boot-oneplus_6t-latest.img`, b2sum `aa064bb24e600ed6f40c7e59c2f5d3c1fc27cfa2eb95d7a2a5a749d6e79c1141...`
- Ядро: `7.1.0-qualcomm-sdm845-alt0.rc1`
- Звуковая карта ALSA: `O6T`

## Симптом

При голосовом звонке собеседник слышит отчётливое эхо своего голоса. Проблема указана в разделе «Известные проблемы» вики как связанная с `q6voice`. Ниже уточнение причины.

## Найденное решение, проверено на устройстве

**Эхо снимается двумя строками в профиле UCM, без патчей к ядру и без калибровки.** Причина акустическая, а не программная.

Профиль распределяет усиление неудачно. Оконечный каскад разговорного динамика `EAR PA Volume` стоит на максимуме (4 из 4, +6 дБ), а цифровое усиление нижнего микрофона `DEC7 Volume` всего 75 из 124. Собеседник слышит пользователя тихо, тот прибавляет громкость клавишами, `RX0 Digital Volume` уходит к 101-110 из 124, динамик пробивается в микрофон, и акустическая петля замыкается. Пользователь эха не слышит, собеседник слышит.

Правка в `BootSequence` файла `/usr/share/alsa/ucm2/OnePlus/fajita/fajita.conf`:

```
cset "name='DEC7 Volume' 85"        # было 75
cset "name='EAR PA Volume' 0"       # было 4, минус 6 дБ
```

Почему именно так. `EAR PA Volume` не упоминается ни в `fajita.conf`, ни в `VoiceCall.conf`, поэтому ни PipeWire, ни клавиши громкости его не трогают. Ослабление на этой ступени сдвигает весь диапазон громкости вниз, и срыв в наводки становится невозможен даже на максимуме шкалы. Убавление микрофона, наоборот, бесполезно: оно приглушает голос и эхо одинаково, соотношения не меняя.

После правки при громкости `RX0` равной 110 (то есть выше той, на которой раньше срывалось) эхо отсутствует, собеседник слышит хорошо, пользователю слышно нормально.

Остаётся нерешённым захват шума окружения: собеседник слышит всё происходящее вокруг. Это та же неработающая цепочка `ECNS`, и акустически она не обходится. `TX7 HPF cut off` уже стоит в максимальном положении `CF_NEG_3DB_150HZ`, других ручек в микшере нет.

## Что установлено про топологии и калибровку

**1. Тракт звонка не проходит через PipeWire.** В `/usr/share/alsa/ucm2/OnePlus/fajita/VoiceCall.conf` используются `SLIMBUS_0_RX Voice Mixer VoiceMMode1` и `VoiceMMode1 Capture Mixer SLIMBUS_0_TX`, то есть голос идёт через сигнальный процессор. Установленный `libpipewire-module-echo-cancel.so` в этом тракте участвовать не может.

**2. Эхоподавление в процессоре запрашивается, но не калибруется.** В `sound/soc/qcom/qdsp6/q6cvp.c` функция `q6cvp_session_create()` содержит комментарий `TODO: Implement calibration` и жёстко задаёт `vocproc_mode = VSS_IVOCPROC_VOCPROC_MODE_EC_INT_MIXING`, `ec_ref_port_id = VSS_IVOCPROC_PORT_ID_NONE`. Значение `PORT_ID_NONE` при внутреннем смешивании корректно, опорный сигнал процессор берёт сам, так что дело не в нём.

**3. Ядро умеет загружать глобальный ACDB, но в дереве устройств не задано имя файла.** В `q6core.ko` присутствуют строки `qcom,acdb-name`, `failed to load Global_cal.acdb`, `ACDB parse error: %d`. Функция `q6core_load_and_register_topologies()` читает свойство `qcom,acdb-name` и при его отсутствии молча возвращает 0. В `arch/arm64/boot/dts/qcom/sdm845-oneplus-common.dtsi` этого свойства нет, узел `q6core` находится по пути `/remoteproc-adsp/glink-edge/apr/service@3`.

Свойство было добавлено вручную через `fdtput` со значением `qcom/sdm845/oneplus-fajita/Global_cal.acdb`, а файл `MTP_Global_cal.acdb` с раздела `vendor_a` положен по этому пути в `/lib/firmware`. После перезагрузки свойство видно в `/sys/firmware/devicetree/base/.../service@3/qcom,acdb-name`, в `dmesg` ни `failed to load`, ни `ACDB parse error` не появилось.

**4. Блок топологий из глобального ACDB не содержит голосовых топологий.** Свойство `0x000131a7` (`ACDB_TOPOLOGIES_BLOB`) находится в `GPROPLUT` по смещению 12772 в `DATAPOOL`, размер 864 байта. Побайтовый поиск идентификаторов `0x00010F71`, `0x00010F72`, `0x00010F77`, `0x00010F89` внутри этого блока не даёт совпадений. То есть регистрация топологий из глобального файла голосовой тракт не затрагивает.

**5. Главное. Топология, заданная в драйвере по умолчанию, отсутствует в заводской калибровке устройства.**

Побайтовый поиск по всем девяти файлам ACDB с раздела `vendor_a` (`/etc/acdbdata/`):

| Топология | Значение | Встречается |
|---|---|---|
| `VSS_IVOCPROC_TOPOLOGY_ID_TX_SM_ECNS` | `0x00010F71` | **0 раз** |
| `VSS_IVOCPROC_TOPOLOGY_ID_TX_SM_ECNS_V2` | `0x00010F89` | 9 раз, из них 4 в `MTP_Handset_cal.acdb` |
| `VSS_IVOCPROC_TOPOLOGY_ID_TX_DM_FLUENCE` | `0x00010F72` | 14 раз, из них 7 в `MTP_Handset_cal.acdb` |
| `VSS_IVOCPROC_TOPOLOGY_ID_RX_DEFAULT` | `0x00010F77` | **0 раз** |
| `VSS_IVOCPROC_TOPOLOGY_ID_NONE` | `0x00010F70` | 4 раза |

`MTP_Handset_cal.acdb` это калибровка разговорного динамика, то есть тракта голосового вызова. Производитель калибровал под него `TX_SM_ECNS_V2` и `TX_DM_FLUENCE`. Первой версии `SM_ECNS`, которую драйвер выбирает по умолчанию, в калибровке этого устройства нет ни в одном файле.

Полная перепись значений из диапазона голосовых топологий в `MTP_Handset_cal.acdb`:

```
0x00010f70  x1     VSS_IVOCPROC_TOPOLOGY_ID_NONE
0x00010f72  x7     VSS_IVOCPROC_TOPOLOGY_ID_TX_DM_FLUENCE
0x00010f73  x12
0x00010f74  x14
0x00010f86  x7
0x00010f87  x7
0x00010f88  x7
0x00010f89  x4     VSS_IVOCPROC_TOPOLOGY_ID_TX_SM_ECNS_V2
0x00010f8b  x1
```

Значения `0x00010f73`, `0x00010f74`, `0x00010f86`, `0x00010f87`, `0x00010f88`, `0x00010f8b` в драйвере не объявлены. При этом `RX_DEFAULT` (`0x00010F77`), который драйвер подставляет как RX-топологию, не встречается ни разу, тогда как приёмный тракт производителем очевидно калибровался. Вероятно, правильная RX-топология находится среди перечисленных неизвестных значений.

**6. Другие топологии процессор не принимает.** Контролы `VoiceMMode1 TX Topology` (numid=99) и `VoiceMMode1 RX Topology` (numid=100) доступны для записи. Значения по умолчанию `69489` = `0x00010F71` и `69495` = `0x00010F77`.

При установке TX в `69513` (`SM_ECNS_V2`) или в `69490` (`DM_FLUENCE`) звонок устанавливается, но **звук отсутствует в обе стороны**, то есть сессия обработки голоса не создаётся. Возврат значения `69489` восстанавливает звук без перезагрузки.

## Воспроизведение

```
amixer -c O6T cget "name=VoiceMMode1 TX Topology"   # 69489
amixer -c O6T cset "name=VoiceMMode1 TX Topology" 69513
# позвонить, звука нет в обе стороны
amixer -c O6T cset "name=VoiceMMode1 TX Topology" 69489
# позвонить, звук есть, эхо у собеседника
```

## Вывод и предложение

Эхо возникает не из-за незагруженной калибровки как таковой, а потому что выбрана цепочка обработки, для которой параметров на этом устройстве не существует. Калибруемые топологии (`SM_ECNS_V2` и `DM_FLUENCE`) недоступны, поскольку голосовая калибровка из файлов устройств в процессор не отправляется, что и отмечено в драйвере как `TODO`.

Что имело бы смысл сделать:

1. Реализовать отправку голосовой калибровки из файлов устройств ACDB командами CVP, это снимет `TODO` в `q6cvp_session_create()`.
2. Добавить свойство `qcom,acdb-name` в дерево устройств для OnePlus 6 и 6T, сейчас загрузка глобального ACDB на этих устройствах не включается вовсе.
3. Пересмотреть значение TX-топологии по умолчанию. Оно указывает на `SM_ECNS` первой версии, которую производители, судя по калибровке этого устройства, не используют.
4. Учесть, что `DM_FLUENCE` требует двух микрофонов, а `VoiceCall.conf` для fajita включает только нижний (`AMIC4`, `MultiMedia2` через `SLIMBUS_0_TX`). Для двухмикрофонной обработки профиль UCM потребуется расширить.

Файлы ACDB, извлечённые с устройства, и скрипты воспроизведения могу приложить по запросу.
