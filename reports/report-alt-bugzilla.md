# Эхо при звонках на OnePlus 6T снимается одним свойством дерева устройств

## Окружение

- Устройство: OnePlus 6T (fajita), загрузчик разблокирован
- Образ: `alt-mobile-phosh-sdm845-latest-aarch64.tar.xz`, b2sum `0283b13f32f1…`
- Загрузчик: `boot-oneplus_6t-latest.img`, b2sum `aa064bb24e60…`
- Ядро: `7.1.0-qualcomm-sdm845-alt0.rc1`, звуковая карта ALSA `O6T`

## Симптом

Собеседник слышит отчётливое эхо своего голоса, шумоподавление не работает.
Проблема указана в разделе «Известные проблемы» вики как связанная с `q6voice`.

## Причина и решение

**Драйвер не отправляет процессору команду применения топологии.**

В `sound/soc/qcom/qdsp6/q6voice.c` предусмотрены две последовательности настройки
обработки голоса:

```c
if (p->v->cvd_v2_3)
	cvp = session_create_v3(...);   /* полная */
else
	cvp = session_create(...);      /* урезанная */
```

Полная последовательность (`session_create_v3`) отправляет описание каналов,
формат портов и, главное, `VSS_IVOCPROC_CMD_TOPOLOGY_COMMIT` (`0x00013198`),
который активирует выбранную цепочку обработки. Урезанная не отправляет ничего
из этого: сессия создаётся с идентификатором топологии, но топология не
применяется, поэтому `ECNS` присутствует формально и не подавляет ни эхо, ни шум.

Выбор делается свойством дерева устройств:

```c
cvd_v2_3 = of_property_read_bool(np, "qcom,cvd-v2.3");   /* q6voice-dai.c */
```

В `arch/arm64/boot/dts/qcom/sdm845-oneplus-common.dtsi` это свойство **не
задано**, поэтому на OnePlus 6 и 6T всегда выбирается урезанный путь. В дереве
для sc7280 свойство выставлено.

**Решение**, проверено на устройстве:

```
fdtput <dtb> /remoteproc-adsp/glink-edge/apr/apr-service@9/dais qcom,cvd-v2.3
```

После перезагрузки в журнале появляется полная последовательность, все команды
принимаются с нулевым статусом:

```
0x13169  создать сессию, версия 3   status 0x0
0x1133d  каналы и форматы, 4 раза    status 0x0
0x13198  применить топологию         status 0x0
0x100c6  включить                    status 0x0
```

Эхо исчезает **даже при заводских громкостях**, включая положение динамика,
при котором раньше эхо было гарантировано. Шумоподавление начинает работать:
речь пользователя проходит поверх ровного шума. Проверено на нескольких живых
звонках.

## Второй дефект: диапазон элемента громкости разговора

В `/usr/share/alsa/ucm2/OnePlus/fajita/VoiceCall.conf` громкостью назначен
элемент `RX0 Digital Volume`:

```
PlaybackVolume "RX0 Digital Volume"
```

Его шкала по данным драйвера это `dBscale-min=-84.00dB, step=1.00dB, max=124`,
то есть значение 84 соответствует 0 дБ, а 124 даёт **плюс 40 дБ**. PipeWire
растягивает свои проценты на всю шкалу, поэтому верхняя треть ползунка подаёт
положительное цифровое усиление и обрезает сигнал.

Последствие неочевидное: обрезание нелинейно, а эхоподавитель строит **линейную**
модель тракта, поэтому остаток становится невычитаемым и **эхо возвращается**.
Пользователь видит связь «прибавил громкость, появилось эхо» и не может её
объяснить. Наблюдалось и воспроизводилось многократно.

Тот же профиль у `SHIFT/axolotl`, то есть дефект не специфичен для OnePlus.

Предложение: назначить громкостью элемент с разумным диапазоном либо ограничить
диапазон средствами драйвера кодека. Средствами UCM ограничить нельзя, такого
параметра в спецификации нет.

## Третий дефект: заниженное усиление микрофона

`BootSequence` в `fajita.conf` задаёт `DEC7 Volume 75`, то есть минус 9 дБ на
микрофоне разговорного тракта. Собеседник слышит тихо. Комфортное значение по
результатам подбора на живых звонках около 80, то есть минус 4 дБ.

## Что осталось нерешённым

Топологии `TX_SM_ECNS_V2` и `TX_DM_FLUENCE` не собираются: процессор отвечает
`ADSP_EFAILED` на `TOPOLOGY_COMMIT`. Причина в отсутствии загрузки заводской
калибровки: в `q6cvp` нет ни поддержки разделяемой памяти (`mem_handle = 0`
везде), ни команд регистрации калибровки. Это и есть `TODO: Implement
calibration` из апстрима.

Важное уточнение, полученное разбором заводской калибровки самого устройства
(файл `/vendor/etc/acdbdata/MTP/MTP_Handset_cal.acdb`). Таблица свойств
устройств `DPROPLUT` содержит для каждого устройства свойство `0x000113af`,
идентификатор топологии:

```
устройство 4  'HANDSET_MIC'          топология 0x00010f89  TX_SM_ECNS_V2
устройство 5  'HANDSET_MIC_...'      топология 0x00010f88
устройство 6  'HANDSET_MIC_ENDFIRE'  топология 0x00010f72  TX_DM_FLUENCE
```

То есть производитель назначил разговорному микрофону **вторую версию**
эхоподавления. Топология `TX_SM_ECNS` первой версии, которую драйвер подставляет
по умолчанию, в девяти файлах калибровки этого устройства не встречается **ни
разу**. Значит значение по умолчанию в драйвере расходится с тем, что предписано
калибровкой, и правильный путь это читать топологию из ACDB, как делает Android.

Сопутствующая правка: число каналов микрофона в `q6cvp` зашито константой 1.
Мы вынесли его в параметр модуля и убедились, что процессор принимает два канала,
но `DM_FLUENCE` всё равно требует калибровки.

## Воспроизведение

```
# до правки: TOPOLOGY_COMMIT не отправляется вовсе
dmesg | grep -c "opcode 0x13198"        # 0

fdtput <dtb> /remoteproc-adsp/glink-edge/apr/apr-service@9/dais qcom,cvd-v2.3
# перезагрузка, звонок
dmesg | grep "opcode 0x13198"           # status: 0x0, эхо исчезло
```

Извлечённая калибровка, скрипты воспроизведения и разборщик формата ACDB
доступны по запросу.
