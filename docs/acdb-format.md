# Формат файлов калибровки Qualcomm ACDB

Собрано побайтовым разбором файлов с OnePlus 6T. Формат проприетарный и
нигде не опубликован. Всё ниже проверено на реальных файлах, неразобранное
помечено явно. Инструмент разбора: `tools/acdb.py`.

## Общий каркас

```
+0   магия     "QCMSNDDB"          8 байт
+8   ?                             8 байт нулей
+16  имя чанка "GCDB"|"AVDB"|"AMDB" 4 байта
...  далее секции подряд, вплотную
```

Каждая секция начинается восьмибайтовым ASCII-именем, затем `u32` длина,
затем `u32` число записей, затем тело. **Секции идут без промежутков**: конец
одной точно совпадает с началом следующей, это удобно для проверки разбора.

## Секции

Для каждого вида калибровки есть тройка `XXXXLUT0`, `XXXXCDFT`, `XXXXCDOT`.

| Префикс | Что калибрует |
|---|---|
| `ACGI`, `ACGD` | звуковой тракт, независимо и зависимо от усиления |
| `AVOL` | громкость |
| `AFEC` | AFE |
| `VDPI` | ? |
| `LSMC` | LSM |
| `ADST` | ? |
| `AANC` | активное шумоподавление |
| **`VPST`** | **статическая калибровка обработки голоса** |
| **`VPDY`** | **динамическая калибровка обработки голоса** |

Плюс `DEVCATIN`, `DPROPLUT` (файлы устройств), `GPROPLUT`, `GLBLLUT`,
`MINFOLUT` (глобальный файл) и `DATAPOOL` в конце.

## Таблицы вида `*LUT`: разобрано

```
имя(8)  u32 длина  u32 число_записей  [записи фиксированного размера]
```

Размер записи равен `(длина - 4) / число_записей`.

**`GPROPLUT`** глобального файла: 13 записей по 8 байт.

```
u32 идентификатор_свойства   u32 смещение_в_DATAPOOL
```

Свойство `0x000131a7` это блок топологий звукового тракта (`ACDB_TOPOLOGIES_BLOB`),
именно его читает патч `q6core` в ядре ALT. Голосовых топологий в нём **нет**.

**`DPROPLUT`** файлов устройств: записи по 12 байт.

```
u32 устройство   u32 идентификатор_свойства   u32 смещение_в_DATAPOOL
```

В `MTP_Handset_cal.acdb` это 383 записи, 37 устройств по 9-12 свойств.

**`VPSTLUT0`**: 292 записи по 24 байта.

```
u32 устройство_TX   u32 устройство_RX
u32 частота_TX      u32 частота_RX      (8000, 16000, 32000, 44100)
u32 ?поле5          u32 ?поле6          НЕ РАЗОБРАНО
```

**`VPDYLUT0`**: 23 записи по 20 байт, первые два поля те же пары устройств.

Пары устройств в `VPSTLUT0`: `4/7`, `4/10`, `4/18`, `4/45`, `5/7`, `6/7`,
`36/17`, `40/7`, `41/7`, `41/9`, `41/10`, `104/103`, `105/103`, `118/7`.

## `DATAPOOL`: разобрано

```
имя(8)  u32 длина  [данные]
```

Данные начинаются **сразу после длины**, поля числа записей нет. По смещению
из любой таблицы лежит запись вида

```
u32 размер   [данные размером size]
```

Строки хранятся в UTF-16LE.

## Свойства устройств: разобрано частично

| Свойство | Значение |
|---|---|
| `0x000113b8` | имя устройства, UTF-16LE |
| `0x000113af` | **идентификатор топологии** |
| `0x000113b3` | идентификатор устройства AFE |
| `0x000113b6`, `0x000113b7`, `0x000113ad`, `0x000113a9` | не разобрано |
| `0x00013150`, `0x00012a4b`, `0x00012ecd`, `0x00012eed`, `0x0001323e` | не разобрано |

Для `MTP_Handset_cal.acdb`:

```
устройство 4  'HANDSET_MIC'          топология 0x00010f89  TX_SM_ECNS_V2
устройство 5  'HANDSET_MIC_...'      топология 0x00010f88
устройство 6  'HANDSET_MIC_ENDFIRE'  топология 0x00010f72  TX_DM_FLUENCE
устройство 7  (приёмный)             свойство 0x113af = 0x1000bff2, похоже на
                                     топологию звукового тракта, не голосового
```

Топология `TX_SM_ECNS` первой версии (`0x00010f71`), которую драйвер `q6cvp`
подставляет константой, **не встречается ни в одном из девяти файлов**.

## `*CDFT` и `*CDOT`: разобрано наполовину

Заголовок такой же, `u32` длина и `u32` число, но **записи не фиксированного
размера**, поэтому деление длины на число даёт нецелые значения (для `VPSTCDFT`
113 байт, для `VPSTCDOT` 891 байт, оба бессмысленны).

Содержимое опознано по значениям.

**`VPSTCDFT`** (длина 2264, число 20): пары идентификаторов.

```
u32 идентификатор_модуля   u32 идентификатор_параметра
0x00010ee1  0x00010e00
0x00010ee1  0x00010e1f
0x00010ee7  0x00010e00
```

Идентификаторы модулей идут по возрастанию, при переходе к следующему набору
должны сбрасываться, это можно использовать для поиска границ.

**`VPSTCDOT`** (длина 17836, число 20): пары «длина, смещение».

```
u32 длина   u32 смещение_в_DATAPOOL
1696  86598
1696  11220
 512   2398
```

`17832 / 8 = 2229` пар ровно.

## Открытый вопрос, на котором остановились

**Как запись `VPSTLUT0` связана со своим набором в `CDFT` и `CDOT`.**

Проверенные и отвергнутые версии:

- Поля 5 и 6 как байтовые смещения в `CDOT` и `CDFT`: смещение 604 не кратно 8,
  значит на пары «длина, смещение» не указывает.
- Поле 5 как смещение прямо в `DATAPOOL`: по нему лежат имена устройств в
  UTF-16, то есть не калибровка.
- `CDFT` и `CDOT` как последовательность «число, затем элементы», повторённая 20
  раз: первое же значение слишком велико для счётчика.

Что стоит попробовать дальше:

1. Разобрать `CDFT` как плоский список пар и найти границы наборов по сбросу
   возрастания идентификатора модуля. Проверить, что наборов получится ровно 20.
2. Сопоставить размеры наборов `CDFT` с размерами наборов `CDOT`: у одного набора
   параметров должно быть столько же смещений, сколько параметров.
3. Проверить поля 5 и 6 как индексы записей, а не байтовые смещения: 1208 и 604
   при делении на 8 дают 151 и 75,5, а при делении на 4 дают 302 и 151. Числа
   151 и 302 подозрительно связаны.
4. Сверить с числом 20: если наборов 20, а пар устройств в `VPSTLUT0` четырнадцать,
   возможно соответствие идёт не по паре устройств, а по чему-то ещё.
