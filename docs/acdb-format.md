# Формат файлов калибровки Qualcomm ACDB

Собрано побайтовым разбором файлов с OnePlus 6T. Формат проприетарный и
нигде не опубликован. Всё ниже проверено на реальных файлах, неразобранное
помечено явно. Инструмент разбора: `tools/acdb.py`.

## Файлы

С раздела `vendor_a`, каталог `/etc/acdbdata/`:

|---|---|---|---|

| `MTP/MTP_Handset_cal.acdb` | 439387 | `AVDB` | калибровка разговорного тракта |
| `MTP/MTP_Speaker_cal.acdb` | 477581 | `AVDB` | громкоговоритель |

## Общий каркас

```
+0   магия     "QCMSNDDB"          8 байт
+8   ?                             8 байт нулей
+16  имя чанка "GCDB"|"AVDB"|"AMDB" 4 байта
...  далее секции подряд, вплотную
```

Каждая секция это восьмибайтовое ASCII-имя, затем `u32` длина, затем ровно
`длина` байт содержимого.

```
имя(8)  u32 длина  [содержимое, ровно «длина» байт]
```

Следующая секция начинается сразу за содержимым, то есть через `12 + длина`
байт от начала предыдущей. **Промежутков между секциями нет**, и это главная
проверка разбора: `acdb.py <файл> sections` идёт по списку известных имён и
сообщает разрыв там, где секция не опознана. На всех девяти файлах разрывов
не остаётся.

Смысл первых четырёх байт содержимого зависит от вида секции, и именно здесь
раньше был неверный разбор. У таблиц `*LUT` это число записей. У секций из
наборов (`*CDFT`, `*CDOT`, `*OFST`, `*CVD0`) это число элементов **первого
набора**, а не счётчик для всей секции. Из-за прочтения его как счётчика
секции терялись последние четыре байта, и разбор наборов не сходился с
границей.

## Секции

Для каждого вида калибровки есть тройка `XXXXLUT0`, `XXXXCDFT`, `XXXXCDOT`,
а у голосовых видов ещё `XXXXOFST` и `XXXXCVD0`.

| Префикс | Что калибрует |
|---|---|
| `ACGI`, `ACGD` | звуковой тракт, независимо и зависимо от усиления |
| `AVOL` | громкость |
| `AFEC`, `AFE ` | AFE (второй префикс с пробелом, отдельная тройка секций) |
| `VDPI` | ? |
| `LSMC` | LSM |
| `ADST` | ? |
| `AANC`, `ANC ` | активное шумоподавление |
| `VVP3`, `AVP3`, `EVP3` | ? пустые или почти пустые |
| **`VPST`** | **статическая калибровка обработки голоса** |
| **`VPDY`** | **динамическая калибровка обработки голоса** |

Плюс `DEVCATIN`, `DPROPLUT` (файлы устройств), `GPROPLUT`, `GLBLLUT`,
`MINFOLUT` (глобальный файл) и `DATAPOOL`. В файлах устройств `DATAPOOL` идёт
последним, в `MTP_Codec_cal.acdb` наоборот вторым, а таблицы за ним.

Кодековый файл живёт по своим правилам: `CPROPLUT`, `WMCA`, `WMCN`, `WSGC`,
`WDMI`, `WMID`, `WDPRPLUT`, `WGPRPLUT`. Это калибровка WCD9340, к голосовому
тракту отношения не имеет и разбиралась только до уровня границ секций.

## Таблицы вида `*LUT`: разобрано

```
имя(8)  u32 длина  u32 число_записей  [записи фиксированного размера]
```

Размер записи равен `(длина - 4) / число_записей`.

**`GPROPLUT`** глобального файла: 13 записей по 8 байт.

```
u32 идентификатор_свойства   u32 смещение_в_DATAPOOL
```

Свойство `0x000131a7` это блок топологий звукового тракта (`ACDB_TOPOLOGIES_BLOB`),
именно его читает патч `q6core` в ядре ALT. Голосовых топологий в нём **нет**.

**`DPROPLUT`** файлов устройств: записи по 12 байт.

```
u32 устройство   u32 идентификатор_свойства   u32 смещение_в_DATAPOOL
```

В `MTP_Handset_cal.acdb` это 383 записи, 37 устройств по 9-12 свойств.

**`VPSTLUT0`**: 292 записи по 24 байта.

```
u32 устройство_TX   u32 устройство_RX
u32 частота_TX      u32 частота_RX      (8000, 16000, 32000, 44100, 48000, 96000, 192000)
u32 смещение_набора_в_VPSTOFST
u32 смещение_набора_в_VPSTCVD0
```

**`VPDYLUT0`**: 23 записи по 20 байт.

```
u32 устройство_TX   u32 устройство_RX
u32 ?поле3          (только 0 и 1)
u32 смещение_набора_в_VPDYOFST
u32 смещение_набора_в_VPDYCVD0
```

Пары устройств в `VPSTLUT0`: `4/7`, `4/10`, `4/18`, `4/45`, `5/7`, `6/7`,
`36/17`, `40/7`, `41/7`, `41/9`, `41/10`, `104/103`, `105/103`, `118/7`.

## `DATAPOOL`: разобрано

```
имя(8)  u32 длина  [данные]
```

Данные начинаются **сразу после длины**, поля числа записей нет. По смещению
из любой таблицы лежит запись вида

```
u32 размер   [данные размером size]
```

Строки хранятся в UTF-16LE.

## Свойства устройств: разобрано частично

| Свойство | Значение |
|---|---|
| `0x000113b8` | имя устройства, UTF-16LE |
| `0x000113af` | **идентификатор топологии** |
| `0x000113b3` | идентификатор устройства AFE |
| `0x000113b6`, `0x000113b7`, `0x000113ad`, `0x000113a9` | не разобрано |
| `0x00013150`, `0x00012a4b`, `0x00012ecd`, `0x00012eed`, `0x0001323e` | не разобрано |

Для `MTP_Handset_cal.acdb`:

```
устройство 4  'HANDSET_MIC'          топология 0x00010f89  TX_SM_ECNS_V2
устройство 5  'HANDSET_MIC_...'      топология 0x00010f88
устройство 6  'HANDSET_MIC_ENDFIRE'  топология 0x00010f72  TX_DM_FLUENCE
устройство 7  (приёмный)             свойство 0x113af = 0x1000bff2, похоже на
                                     топологию звукового тракта, не голосового
```

Топология `TX_SM_ECNS` первой версии (`0x00010f71`), которую драйвер `q6cvp`
подставляет константой, **не встречается ни в одном из девяти файлов**.

## Секции из наборов: разобрано

`*CDFT`, `*CDOT`, `*OFST`, `*CVD0` устроены одинаково. Содержимое секции это
идущие подряд наборы, каждый набор начинается своим счётчиком.

```
u32 число_элементов   [элементы фиксированного для секции размера]
u32 число_элементов   [элементы]
...
```

Ссылаются на набор по смещению его собственного поля `число_элементов` внутри
содержимого секции. Поэтому смещения наборов не кратны размеру элемента, и
проверка «не кратно восьми, значит не смещение» в прошлый раз сбила разбор с
пути.

Размер элемента по виду секции:

| Секция | Элемент | Что в нём |
|---|---|---|
| `*CDFT` | 8 байт | `u32` идентификатор модуля, `u32` идентификатор параметра |
| `*CDOT` | 4 байта | `u32` смещение в `DATAPOOL` |
| `*OFST` | 8 байт | `u32` смещение набора в `*CDFT`, `u32` смещение набора в `*CDOT` |
| `VPSTCVD0` | 28 байт | ключ запроса со стороны CVD, 7 слов |
| `VPDYCVD0` | 32 байта | тот же ключ плюс ступень громкости, 8 слов |

Для `MTP_Handset_cal.acdb`: `VPSTCDFT` 16 наборов и 275 пар, `VPSTCDOT` 217
наборов и 4242 смещения, `VPSTOFST` 33 набора и 2451 пара, `VPSTCVD0` 2 набора
и 126 записей. Разбор каждой секции кончается ровно на её границе.

Исключение: в `MTP_Codec_cal.acdb` секции `WMCACDFT`, `WMCNCDFT`, `WSGCCDFT`,
`WMIDCDFT` под восьмибайтовый элемент не встают. Похоже, у кодека в `CDFT`
лежат одиночные идентификаторы регистров по 4 байта (`0x00012c25` и подобные),
но однозначно это не подтверждается, и на голосовой тракт не влияет.

## Как найти калибровку: цепочка целиком

Это и был открытый вопрос прошлого сеанса. Ответ: между `LUT` и парой
`CDFT`/`CDOT` стоят ещё две секции, `OFST` и `CVD0`, и они не были опознаны,
потому что их имена отсутствовали в списке искомых.

```
VPSTLUT0: устройство_TX, устройство_RX, частота_TX, частота_RX
    -> смещение в VPSTOFST и смещение в VPSTCVD0

VPSTOFST[смещение]: N пар (смещение_CDFT, смещение_CDOT)
VPSTCVD0[смещение]: те же N записей, ключ CVD для каждой пары

VPSTCDFT[смещение_CDFT]: M пар (модуль, параметр)
VPSTCDOT[смещение_CDOT]: те же M смещений в DATAPOOL

DATAPOOL[смещение]: u32 размер, затем данные параметра
```

То есть строка `LUT` задаёт устройства и частоты, набор `OFST` перечисляет все
варианты для этой пары, запись `CVD0` говорит, при каком запросе от CVD берётся
вариант, а пара наборов `CDFT`/`CDOT` даёт список параметров и их данные.

Чем проверено:

- у всех 2451 пары `VPSTOFST` число пар в наборе `CDFT` равно числу смещений в
  наборе `CDOT`, расхождений нет; для `VPDYOFST` то же на всех 5986 парах;
- у каждой строки `LUT` размер набора `OFST` равен размеру набора `CVD0`
  (75 и 75, 51 и 51 для статической таблицы разговорного динамика);
- все 4242 смещения `VPSTCDOT` попадают внутрь `DATAPOOL`, размеры записей
  правдоподобны, за границу не выходит ни одна;
- разбор всех четырёх секций кончается ровно на границе секции.

Команда `acdb.py <файл> cal <TX> <RX> [--dyn] [--entry N]` проходит цепочку.
Для разговорного тракта (`cal 4 7`) это 20 строк `LUT`, в каждой 75 вариантов,
на вариант от 15 до 21 параметра, всего 17364 байта данных на строку.

Параметр `0x00010e00` при размере 4 байта это включение модуля, значение 1 или
0. Записи `DATAPOOL` разделяются между наборами: смещение 512 хранит единицу,
смещение 1696 ноль, и на них ссылаются десятки наборов.

Побочное наблюдение по паре `4/7` на частотах 8 кГц: среди всех 75 вариантов
единицу в этом параметре получает только модуль `0x00010f1f`, у остальных
девяти модулей стоит ноль. Что это значит, пока непонятно: то ли включение
приходит не из статической таблицы, то ли модуль включается самим выбором
топологии.

## Ключ `CVD0`: разобрано частично

Семь слов статической записи, на примере первой записи набора 0
разговорного файла:

```
w0  0x0001135f   пять значений, 0x1135f..0x11363
w1  0            частота одного направления, из 0, 8000, 16000, 32000, 48000
w2  8000         частота другого направления, тот же набор значений
w3  0x00013085   три значения, 0x13085..0x13087, идёт вместе с w1
w4  0x00013085   те же три значения, идёт вместе с w2
w5  0x00010fc0   диапазон 0x10fc0..0x10fd8
w6  0x0001308a   0x1308a, 0x1308b, 0x1308c, 0x130a7
```

У динамической записи после `w2` вставлено восьмое слово со ступенью
громкости, значения 0..5, дальше поля те же.

Что видно из данных:

- в записи всегда ненулевая ровно одна из частот `w1` и `w2`, то есть вариант
  описывает одно направление, передачу или приём;
- меняется то из слов `w3`, `w4`, которое стоит в паре с ненулевой частотой,
  так что слова связаны попарно: `(w1, w3)` и `(w2, w4)`. Какая пара
  относится к передаче, а какая к приёму, взято по порядку полей в
  `VPSTLUT0`, отдельной проверки на это нет;
- `w0` растёт вместе с допустимой частотой: при `0x1135f` встречаются только
  8 и 16 кГц, при `0x11362` и `0x11363` появляются 32 и 48 кГц. Похоже на класс
  сети или полосу, но подтвердить нечем;
- диапазон `w5` совпадает с диапазоном `VSS_MEDIA_ID_*` из интерфейса CVD, то
  есть это, скорее всего, тип вокодера. Это предположение, не проверка.

Имена для `w0`, `w3`, `w4`, `w6` не установлены. Для отправки калибровки это и
не требуется: достаточно выбрать запись по паре устройств, частотам и
направлению, а остальные поля сравнивать с тем, что запрашивает CVD.

## Открытые вопросы

1. Значения `w0`, `w3`, `w4`, `w6` ключа `CVD0`. Проверяемый путь: снять с
   заводской прошивки лог `acdb-loader` или сопоставить с перечислениями
   заголовков CVD, если они найдутся в открытом виде.
2. Поле 3 таблицы `VPDYLUT0`, принимающее только 0 и 1.
3. Размер элемента в `CDFT` кодековых таблиц `W*`.
4. Не разобранные свойства устройств из таблицы выше.
