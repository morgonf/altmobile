# Почему `TOPOLOGY_COMMIT` отказывает: разбор прошивки процессора

Разобрана прошивка ADSP, которую телефон действительно грузит. Путь виден в
журнале ядра, строка `Booting fw image qcom/sdm845/OnePlus/enchilada/adsp.mbn,
size 11128744`, а сам файл лежит в
`/lib/firmware/droid-juicer/qcom/sdm845/OnePlus/enchilada/adsp.mbn`, куда его
положил `droid-juicer`, вытащив из заводской прошивки. Формат ELF 32 бита,
`QUALCOMM DSP6`, 14 сегментов с данными.

Сразу отпала версия про подменённую прошивку. Обобщённый образ из
`linux-firmware` (`/lib/firmware/qcom/sdm845/adsp.mbn.xz`, 10425168 байт после
распаковки) от заводского отличается, но идентификаторы голосовых топологий в
обоих встречаются одинаковое число раз, и лицензионный механизм в обоих тот же.

## Таблица числа микрофонов

В прошивке лежит таблица пар «топология, число микрофонов».

| Топология | Микрофонов |
|---|---|
| `0x10f70` `TOPOLOGY_ID_NONE` | 1 |
| `0x10f71` `TX_SM_ECNS` | 1 |
| `0x10f73` | 1 |
| `0x10f89` `TX_SM_ECNS_V2` | 1 |
| `0x10027000`..`0x10027002` | 1 |
| `0x10f72` `TX_DM_FLUENCE` | 2 |
| `0x10f74` | 2 |
| `0x10f88` | 2 |
| `0x10f86` | 2 |
| `0x10027010`..`0x10027012` | 2 |
| `0x10f87` | 4 |
| `0x10027020`..`0x10027022` | 4 |

Отсюда сразу следствие: **второй версии ECNS хватает одного микрофона**, и
версия про число каналов к её отказу отношения не имеет. Двух микрофонов требуют
`DM_FLUENCE` и `0x10f88`, а четырёх `0x10f87`.

## Списки модулей по топологиям

Рядом лежит таблица записей вида «идентификатор топологии, 8, число модулей,
адрес списка, 0». Адрес переводится в смещение в файле по заголовкам ELF, после
чего список читается целиком.

```
0x10f70 NONE           1 модуль
    00010f1e

0x10f71 TX_SM_ECNS    12 модулей
    00010f11 00010ef7 00010ef0 00010f01 00010f1e 00010ee0
    00010f1b 00010ee9 00010ee7 00010f00 00010ef3 00010ef4

0x10f73               12 модулей
    00010f11 00010ef7 00010ef0 00010f01 00010f1e 00010f09
    00010f1b 00010ee9 00010ee7 00010f00 00010ef3 00010ef4

0x10f89 TX_SM_ECNS_V2 12 модулей
    00010f11 00010ef7 00010ef0 00010f01 00010f1e 00010f1f
    00010f1b 00010ee9 00010ee7 00010f00 00010ef3 00010ef4

0x10f72 TX_DM_FLUENCE 13 модулей
    00010f11 00010ef7 00010ef0 00010ef1 00010f01 00010f1e 00010ee1
    00010f1b 00010ee9 00010ee7 00010f00 00010ef3 00010ef4
```

Цепочки отличаются **ровно одним модулем**, это и есть сам подавитель:

| Топология | Модуль подавителя |
|---|---|
| `TX_SM_ECNS` первой версии | `0x00010ee0` |
| `TX_SM_ECNS_V2` | `0x00010f1f` |
| `TX_DM_FLUENCE` | `0x00010ee1`, плюс добавлен `0x00010ef1` |

Сходится с разбором калибровки: единственным модулем, которому заводская
статическая калибровка пары устройств `4/7` ставит «включён», оказался именно
`0x00010f1f`, см. `acdb-format.md`.

## Регистр модулей с признаком

Модуль `0x00010ee0`, которым пользуется работающая первая версия, лежит в одной
структуре прошивки, а `0x00010f1f` и `0x00010ee1` совсем в другой. Эта другая
содержит 23 записи по 28 байт вида «указатель, указатель, 0, идентификатор
модуля, 0, признак 1, признак 2». Первый признак у всех единица, второй
различается.

Признак 2 равен единице у:

```
00010ee1  TX_DM_FLUENCE
00010f16  00010f09  00010f0a  00010f17  00010f18
00010f1f  TX_SM_ECNS_V2
10027050  10027051  10027053  10027054  10027056  10027057
```

Признак 2 равен нулю у:

```
00010916  0001077c  0001077b  00010933
10027052  10027055  10027058
00012c0d  00012c1c  00012c22
```

То есть в один список с единицей попали ровно семейство Fluence, вторая версия
ECNS и часть заказных модулей `0x1002705x`. Модулей работающих топологий в этой
таблице нет вовсе.

## Вывод

В прошивке есть база лицензий и работа с ней. Строки прямые:

```
adsp_license_db_get_license
adsp_license_db_get_size
AdspCoreSvc_Utils.cpp:No license exists with id %lu
AdspCoreSvc_Utils.cpp:License with id %lu has not bee...
AdspCoreSvc_Utils.cpp:License with id %lu already exi...
Svc_Utils.cpp:Mismatch in license size. Expected %lu Got
...cpp:AvsCoreSvc: Get License Validation Result Respo...
...ent size received for set license.
...the overwrite flag in set license command.
...cpp:Failed to initialize license database!
```

Складывая всё вместе: `TX_SM_ECNS_V2` и семейство `Fluence` собраны из модулей,
отмеченных в прошивке отдельным признаком и лежащих в отдельном регистре, а
процессор умеет требовать лицензию по идентификатору. Топологии, чьи модули этим
признаком не отмечены, собираются без вопросов. Это объясняет, почему
`TOPOLOGY_COMMIT` отказывает одинаково при любом идентификаторе сети, при любом
числе каналов и при живых определениях топологий в прошивке.

Утверждение про лицензию это **вывод по совокупности признаков, а не
доказательство**. Прямой проверки пока нет, для неё нужно найти, чем
инициализируется база лицензий и есть ли на устройстве лицензионные данные.

## Закономерность, подтверждённая на живых звонках

Сопоставление таблицы модулей с результатами `TOPOLOGY_COMMIT` даёт правило без
исключений на всех проверенных случаях.

| Топология | Отличительный модуль | В особом регистре | Сборка |
|---|---|---|---|
| `0x10f70` `NONE` | `0x10f1e` | нет | прошла |
| `0x10f71` `TX_SM_ECNS` | `0x00010ee0` | нет | прошла |
| `0x10f89` `TX_SM_ECNS_V2` | `0x00010f1f` | да | отказ |
| `0x10f72` `TX_DM_FLUENCE` | `0x00010ee1` | да | отказ |
| `0x10f88` | `0x00010f18` | да | отказ |

Четыре из четырёх проверенных сходятся. Предсказание для непроверенных:
`0x10f73` (`0x10f09`), `0x10f74` (`0x10f0a`), `0x10f86` (`0x10f16`) и `0x10f87`
(`0x10f17`) тоже должны отказать, потому что все их отличительные модули в том же
регистре.

Из этого же следует, что собираться могут ровно две топологии передачи, пустая и
односмикрофонная первой версии. Всё остальное, что OnePlus прописал своим
устройствам, недоступно.

## Первая версия подавителя оказалась слабой

Проверено на живых звонках. Модуль `0x00010ee0` был **выключен**, его включение
одной командой дало слышимое улучшение, собеседник стал слышать своё эхо тише.
Но дальше упор: пять наборов коэффициентов подавителя второй версии
(`0x10e61`, `0x10e62`, `0x10e63`, `0x10e82`, `0x10eab`) процессор от имени
первой версии **принял без ошибок**, а на слух ничего не изменилось. Значит за
теми же номерами параметров в первой версии стоит другая начинка, либо модуль
принимает и откладывает.

Похоже, `0x00010ee0` это старый блок, в котором настоящего вычитания эха нет, а
есть лишь простое подавление. Настоящее вычитание живёт в модулях особого
регистра, то есть в том, что недоступно.

## Лицензионных данных не найдено нигде

Проверено: на разделах `dsp_a`, `persist`, `vendor_a` лицензий для звука нет, там
только Widevine для видео. В девяти файлах ACDB строки `licen` в любом виде нет.
Неразобранные свойства глобального файла тоже проверены: `0x0001308f` и
`0x00012e47` действительно содержат идентификаторы модулей особого регистра, но
это блоки заказных топологий звукового тракта, в них текст `AUDIO_DS2_CUST`.

## Что проверять дальше

1. Найти, откуда берётся содержимое базы лицензий. Искать лицензионные данные на
   разделах устройства, в первую очередь `dsp_a`, `persist`, `vendor_a`.
2. Посмотреть в заводском драйвере, кто и когда отправляет
   `AVCS_CMD_SET_LICENSE`, с какими идентификаторами и откуда берёт ключ.
3. Если лицензия отправляется с хоста, добавить эту команду в `q6core` и
   проверить `TOPOLOGY_COMMIT` снова. Если лицензия должна быть внутри прошивки,
   выяснить, почему база не инициализируется.
